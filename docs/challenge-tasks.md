# Challenge Tasks

1. **Preference-shift task:** stakeholder preference weights change mid-episode (e.g. priority reweighted from speed to quality partway through). Baselines with no mechanism to re-anchor to updated preferences are expected to keep optimizing the stale objective.
   - **Injection timing:** proportional to each workflow's configured timestep budget, not a fixed step count, so the same relative timing applies regardless of episode length. The shift is injected at a single specific timestep (e.g. t = 0.33 x episode_length), not within a range. Three depths are defined: **early** (33%), **mid** (50%), and **late** (67%) of the episode. The mid depth is included so degradation can be read as a trend across three points rather than inferred from two endpoints alone, consistent with this project's own evaluation methodology (see Evaluation Question 2 in docs/metrics.md, which explicitly calls for degradation slope rather than endpoints only).
   - **Confound control:** if the target workflow has a native/scripted preference shift already defined, disable it for this task's runs and inject the controlled shift at the chosen depth instead, so any measured effect is attributable to the injected shift alone. Also freeze team composition (disable native worker join/leave events) for this task's runs, so churn does not confound the measured preference-shift effect.
2. **Team-churn task:** a worker leaves or joins mid-episode, forcing reassignment across the remaining/new team. Baselines with no representation of the change are expected to fail to adapt allocation.
   - **Injection timing:** same proportional depth convention as the preference-shift task (early 33%, mid 50%, late 67% of episode budget), applied to when the join/leave event occurs at that single specific timestep.
   - **Isolation requirement:** inject a single, controlled join or leave event per run rather than relying on a workflow's native churn schedule, which tends to cluster multiple changes close together and makes it impossible to attribute a performance change to one specific event. Disable native churn scheduling for this task's runs. Also freeze preference weights (disable any native preference shift) so churn is tested in isolation from preference drift.
3. **Compound task:** both preference shift and team churn occur within the same episode – the joint stress case directly corresponding to the MA-Gym paper's open problem. This is the one task where both native or injected preference shift AND team churn are deliberately allowed to co-occur (at independently chosen depths), since it is testing the joint stress case on purpose.
4. **Cross-episode task:** a sequence of related but distinct workflows is run consecutively with no retraining between them, testing whether Phase 3's memory produces measurable improvement across the sequence – the direct test of the "continual" claim, as opposed to within-episode replanning alone.
